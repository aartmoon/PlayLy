# Архитектура Android PlayLy

## Статус решения

Выбрано направление развития Android-клиента:

- Kotlin и однонаправленный поток данных с элементами Elm, MVI и MVVM.
- Dagger 2 для внедрения зависимостей.
- Jetpack Compose для интерфейса приложения.
- Phaser для игрового исполнения в отдельном Android WebView-плеере согласно [общей спецификации](../../docs/game-generation.md).

Каркас приложения включает Compose-экраны, Dagger 2, обработку сообщений в ViewModel и OkHttp/Moshi-клиент из корневого `OpenApi.yml`. Каталог, вход, профиль, проекты, отправка промпта и опрос статуса подключены к Core. WebView-плеер открывает проверенные веб-пакеты v2 из каталога, истории версий и экрана генерации.

Для Android-эмулятора debug-сборка использует `http://10.0.2.2:8080/api/v1`. Другой адрес задаётся Gradle-свойством `playlyCoreUrl`. Отладочный HTTP разрешён для адресов эмулятора и localhost. Release-сборке нужен HTTPS-адрес в `playlyReleaseCoreUrl`.

## Ответственность частей архитектуры

| Часть | Ответственность |
|---|---|
| Compose UI | Отображает состояние фичи и передаёт пользовательские действия; управляет локальным визуальным состоянием |
| ViewModel | Владеет состоянием и обработкой сообщений фичи, связывает их с жизненным циклом Android |
| State | Неизменяемое состояние фичи, необходимое для отображения и принятия решений |
| Message | Действие пользователя или результат асинхронной операции |
| Update / reducer | Чистая функция перехода: состояние и сообщение превращаются в новое состояние и команды |
| Command handler | Выполняет команды через репозитории/use cases и возвращает результаты сообщениями |
| Repository | Предоставляет данные и операции, скрывает сетевой клиент, хранение и кеширование |
| Use case | Выделяет сложную или переиспользуемую операцию, когда это необходимо |
| Dagger 2 | Собирает зависимости; время жизни компонентов определяется временем жизни их владельцев |
| WebView Player | Загружает проверенный локальный веб-пакет, управляет lifecycle и изоляцией игрового WebView; Phaser исполняет игровые сцены |

Elm задаёт разделение чистых переходов и внешних операций, MVI — явный поток сообщений и состояния, MVVM — интеграцию с Android ViewModel. Эти названия обозначают роли внутри одного подхода.

## Поток данных фичи

1. UI передаёт сообщение в ViewModel.
2. Сообщение последовательно обрабатывается функцией `update(state, message)`.
3. Новое состояние публикуется в `StateFlow`; Compose наблюдает его с учётом lifecycle.
4. Полученные команды выполняются отдельно от чистой функции обновления.
5. Результаты команд возвращаются сообщениями в тот же поток обработки.

Длительные операции выполняются асинхронно. Последовательное применение сообщений не означает, что сетевой запрос блокирует обработку остальных действий. Для каждой операции задаются правила конкуренции, повторов и отмены; устаревший ответ не должен заменять актуальные данные.

Чистые переходы тестируются без сети и Android. Обработчики команд проверяются отдельно с подменными зависимостями. Общие абстракции выделяются после проверки на реальных фичах.

## Генерация и восстановление

Пример последовательности: `GenerateClicked` → команда отправки запроса → `GenerationAccepted(id)` → наблюдение статуса → сообщение о готовой версии или ошибке.

- Повтор принятого запроса соблюдает контракт `Idempotency-Key`.
- Данные, необходимые для восстановления запроса/задания после завершения процесса, сохраняются вне ViewModel; конкретное хранилище выбирается при реализации.
- Core остаётся источником статуса серверного задания. При восстановлении клиент запрашивает актуальное состояние.
- Завершение локального наблюдения при уходе с экрана не означает отмену серверной генерации.
- Успех операции и идентификатор результата отражаются в состоянии/данных. Очередь одноразовых UI-событий не является единственным местом хранения значимого результата.
- Навигация и кратковременные UI-действия учитывают lifecycle и повторное появление экрана; описание команды само по себе не гарантирует выполнение ровно один раз.

## Зависимости и границы

- Используется Dagger 2; Hilt не выбран.
- Предпочтительно внедрение зависимостей через конструкторы.
- Сгенерированный API-клиент используется за границей репозитория/адаптера. Генерируемые DTO не определяют структуру состояния экрана.
- Чистая логика переходов и проверки пакетов не зависит от Compose, Android ViewModel и компонентов DI. Android WebView изолируется в слое плеера; игровая логика Phaser находится в собранном веб-пакете.
- Сессия и общие данные могут иметь владельца на уровне приложения; у каждой фичи своё состояние. Один глобальный Store не является требованием.
- Физическое разбиение на Gradle-модули определяется по мере реализации; границы ответственности соблюдаются с первых фич.

## Интерфейс приложения и игры

Compose с Material Design 3 используется для авторизации, каталога, редактора, профиля и интерфейса вокруг запуска игры. [Правила UI](ui.md) задают требования к компонентам, ресурсам, отступам и проверке экранов. Игровые сцены Phaser имеют собственное состояние, цикл исполнения и renderer внутри WebView. Покадровое состояние мира не проходит через экранный reducer/ViewModel.

По обновлённой спецификации AI генерирует TypeScript для Phaser. Серверный runner собирает и проверяет веб-пакет; Android загружает его и исполняет собранный JavaScript в изолированном WebView. Пакет v2 использует `game.json` как дескриптор загрузки, а не описание всех игровых правил. Старый формат v1 не переинтерпретируется как v2.

Game Loader проверяет пути, размеры, SHA-256 и совместимость пакета, затем атомарно активирует локальный кеш. Плеер использует контролируемый локальный HTTPS-origin и ограничения из раздела 10 общей спецификации. Игра не получает токены Core и доступ к данным приложения. Управление паузой, выходом и освобождением WebView остаётся у Android-оболочки.
