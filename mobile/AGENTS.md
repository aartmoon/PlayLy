# Правила Android-части PlayLy

## Источники решений

- Перед изменением Android-логики, DI или структуры прочитайте [архитектуру](docs/architecture.md).
- Перед созданием или изменением экрана прочитайте [правила UI](docs/ui.md) и соответствующий сценарий в [экранах MVP](docs/screens.md).
- Общая архитектура и ограничения продукта — в [README](../README.md), HTTP-контракт — в [OpenApi.yml](../OpenApi.yml). При интеграции API прочитайте соответствующие операции и схемы.
- При работе с загрузкой или плеером прочитайте разделы 9–10 [спецификации веб-игр](../docs/game-generation.md). Целевая платформа — Phaser в Android WebView; Core пока использует пакет v1, переход на v2 ещё не реализован.
- Отличайте выбранные решения от реализованных возможностей. Реализованы начальные Compose-экраны, работа с Core и Dagger 2. Статус Android-плеера описан в архитектуре.

## Выбранный стек

- Kotlin, однонаправленный поток данных с элементами Elm, MVI и MVVM.
- Состояние фичи неизменяемое; переходы описываются чистой функцией `update(state, message)`, возвращающей новое состояние и команды.
- Команды выполняются отдельно от функции обновления через репозитории и при необходимости use cases. Результаты возвращаются сообщениями.
- Android `ViewModel` владеет обработкой сообщений и жизненным циклом корутин фичи; UI получает состояние через `StateFlow`.
- Сообщения изменяют состояние последовательно. Для асинхронных операций явно определяйте поведение повторов, отмены и устаревших результатов.
- DI — Dagger 2. Сохраняйте этот выбор; переход на Hilt или другой DI является отдельным изменением архитектурного решения.
- Jetpack Compose с Material Design 3 используется для интерфейса приложения. Игровая сцена исполняется Phaser в отдельном WebView-плеере согласно общей спецификации; Android-плеер ещё предстоит внедрить.
- Расширяйте общую инфраструктуру по потребностям реализуемых фич. Сначала проверяйте подход на рабочем сценарии, затем выделяйте общие абстракции.

## Контракты и данные

- Не редактируйте исходники в `app/build/generated/`: они пересоздаются Gradle. Меняйте исходный контракт либо собственные адаптеры и репозитории.
- Android обращается к Core API с префиксом `/api/v1`. Kafka и AI остаются внутренними серверными компонентами.
- Соблюдайте контракт ротации refresh token, идемпотентности генерации, polling, дедлайнов и совместимости игровых пакетов.
- Значимые результаты операций отражайте в состоянии. Для восстановления после завершения процесса используйте сохраняемые данные и повторное чтение состояния Core; одна ViewModel или очередь UI-событий этого не обеспечивает.
- Не храните токены и пароли в логах или коммитах. Явно обозначайте mock-данные и неподключённые сценарии.

## UI и ресурсы

- Соблюдайте Material Design 3: используйте Material-компоненты, цвета/типографику/формы темы и централизованные spacing-токены по `docs/ui.md`.
- Статические пользовательские строки, включая сообщения ошибок и accessibility-описания, храните в ресурсах `strings.xml`; используйте `stringResource`, форматирование и `plurals`. Пользовательский и серверный контент остаётся данными.
- Учитывайте доступность, область нажатия от 48 × 48 dp, системные отступы, клавиатуру, увеличенный шрифт, тёмную тему и длинные тексты.

## Проверка изменений

- При ошибках Sync/сборки сначала изучайте конкретную ошибку и окружение. Изменения AGP, Gradle, Kotlin и JDK проверяйте на совместимость с Android Studio и CI.
- Используйте Gradle Wrapper проекта. Из `mobile/`: `./gradlew :app:assembleDebug :app:lintDebug :app:testDebugUnitTest`; в PowerShell — `.\gradlew.bat` с теми же задачами.
- Выбирайте проверки по изменению: для логики переходов и команд нужны содержательные тесты; для UI проверяйте соответствующие состояния на эмуляторе или устройстве, когда это доступно. Для правок только документации достаточно проверить diff и актуальность ссылок.
- В отчёте разделяйте успешную сборку, тесты, запуск UI и проверку с настоящим сервером. Указывайте непроверенные части.
- Сохраняйте чужие и локальные изменения; не коммитьте `local.properties` и содержимое `build/`.
