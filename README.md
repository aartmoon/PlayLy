# PlayLy (ПлейЛи)
## Техническая аннотация проекта

### 1. Общая информация

**Название:** PlayLy (ПлейЛи)

**Тип проекта:** мобильное приложение с использованием искусственного интеллекта для генерации интерактивных 2D-игр.

**Целевая платформа:** Android.

**Цель проекта:** разработать мобильную платформу, позволяющую пользователям создавать, изменять, запускать и публиковать 2D-игры с помощью текстовых запросов на естественном языке без необходимости владеть навыками программирования.

### 2. Описание проекта

PlayLy — мобильная платформа для создания и распространения интерактивных 2D-игр с использованием генеративного искусственного интеллекта.

Пользователь описывает игру текстовым запросом. LLM генерирует TypeScript-код для Phaser, используя заготовки PlayLy и собственные игровые механики. Сервер проверяет содержание, компилирует и тестирует игру в изолированной песочнице, оценивает соответствие запросу и только после успешных проверок сохраняет готовый веб-пакет в RustFS. Android скачивает пакет и запускает его в WebView.

Пользователь может изменять существующие игры дополнительными текстовыми запросами, сохранять версии, публиковать результаты в общем каталоге, запускать игры других пользователей и оценивать их.

Подробная целевая спецификация: [генерация TypeScript, Phaser, песочница, Langfuse и WebView](docs/game-generation.md). Она заменяет прежний подход GameSpec/libGDX; текущая реализация Core пока использует контракт пакета версии 1, переход на версию 2 требует отдельных изменений кода.

### 4. Архитектура системы

Система проектируется на основе облегчённой микросервисной архитектуры с двумя независимо развёртываемыми серверными сервисами.

**4.1. Core Service**

Основной серверный сервис, реализующий бизнес-логику приложения и предоставляющий REST API для Android-клиента.

Внутренние модули:

- **Auth & Users** — регистрация, авторизация, профили пользователей.
- **Games & Versions** — управление играми, метаданными и версиями.
- **Catalog & Ratings** — публикация, поиск и оценки игр.
- **Generation Jobs** — создание заданий генерации, управление их состояниями и обработка результатов.
- **Storage Integration** — управление объектами в RustFS.

Core Service является владельцем основной базы данных и отвечает за согласованность пользовательских и игровых данных.

**4.2. AI Generation Service**

Независимый сервис асинхронной обработки запросов на создание и изменение игр.

Функции:
- Получение заданий из Apache Kafka.
- Подготовка промптов и контекста существующей игры.
- Взаимодействие с внешним LLM API.
- Генерация и модификация TypeScript-кода и подбор ресурсов.
- Модерация, изолированная сборка и браузерное тестирование.
- Проверка соответствия запросу и запись оценок в Langfuse.
- Сохранение в RustFS только прошедших обязательные проверки пакетов и закрытых исходников.
- Публикация сообщений об успешном выполнении или ошибке через Kafka.

Сервис не обращается напрямую к базе данных Core Service. Данные задания и ключи исходных объектов RustFS передаются через Kafka; результаты возвращаются в Core через Kafka. Авторизация пользователей, управление заданиями и создание версий остаются ответственностью Core. AI не выдаёт пользовательские токены и не предоставляет клиентских HTTP-ручек.

**4.3. Android Application**

Мобильный клиент содержит интерфейс на Jetpack Compose и игровой экран Android WebView с Phaser.

Основные компоненты:
- Авторизация и профиль.
- Редактор текстовых запросов.
- Управление игровыми проектами.
- Каталог опубликованных игр.
- Game Loader — загрузка и кеширование игровых файлов.
- WebView Player — запуск локального проверенного веб-пакета в ограниченной среде.
- Phaser — сцены, игровая логика, ввод, физика и отрисовка внутри WebView.

### 6. Генерация и исполнение игр

Целевая модель: пользовательский промпт → TypeScript для Phaser → валидация и модерация → проверка типов и сборка Vite в песочнице → браузерные тесты → оценка соответствия промпту → RustFS → Android WebView.

TypeScript собирается на сервере в JavaScript. Phaser работает в браузерной среде WebView; компиляция на телефоне не требуется. AI может использовать наши заготовки и создавать собственные сцены и механики в пределах разрешённого Phaser API. Зависимости, конфигурация сборки и оболочка задаются платформой.

До загрузки файлов игры в S3 обязательны успешная сборка, тестовый запуск, модерация текста и ресурсов и оценка выполнения требований пользователя. AI-воркер синхронно получает обязательные оценки, используя версионированные промпты из Langfuse, и записывает scores. Асинхронные online evaluators дополняют мониторинг; поздняя оценка не заменяет проверку перед выдачей.

Полные контракты, ограничения песочницы и WebView, формат пакета, правила отказа и критерии приёмки описаны в [спецификации генерации](docs/game-generation.md). В новом пакете `game.json` — дескриптор загрузки, игровые правила находятся в JavaScript. Переход на `gameSpecVersion: 2.0` и `runtimeVersion: 2.0.0` требует обновления Core, Kafka-схем и Android; текущая реализация версии 1 сохраняется до этого перехода. ### 7. Взаимодействие компонентов

**7.1. Синхронное взаимодействие**

Android взаимодействует с Core Service по HTTPS посредством REST API.

Используется для:
- Регистрации и авторизации.
- Получения профиля и списка игр.
- Просмотра каталога.
- Отправки заданий на генерацию.
- Получения статуса генерации.
- Публикации и оценки игр.

Контракт внешнего API описан в [OpenApi.yml](OpenApi.yml). Все HTTP-ручки реализует Core Service; AI Generation Service взаимодействует с ним через Kafka.

Регистрация и вход выполняются по email и паролю в Core. Email уникален без учёта регистра и нормализуется удалением пробелов по краям; пароль не нормализуется и хранится только как стойкий хеш. Core выдаёт JWT access token и непрозрачный refresh token. Сроки действия возвращаются в секундах в `expiresIn` и `refreshExpiresIn`.

При обновлении refresh token атомарно заменяется и становится недействительным после использования. Клиент обновляет токены последовательно. Выход отзывает указанную refresh-сессию; уже выданный access token действует до истечения срока. Клиент удаляет оба токена.

Каталог, карточки опубликованных игр, метаданные опубликованных версий и ссылки на их пакеты доступны без входа. Если клиент передал недействительный access token, возвращается 401. Черновики и история версий и генераций доступны только владельцу. Отсутствующий или недоступный ресурс возвращает 404. Оценки требуют авторизации и относятся к игре, сохраняясь при смене опубликованной версии. Все операции с оценкой доступны только для опубликованной игры; после снятия с публикации возвращается 404, сохранённые оценки вновь доступны при повторной публикации. Автор не может оценить собственную игру: PUT возвращает 409 с кодом `SELF_RATING_FORBIDDEN`.

Карточка игры содержит публичные данные автора `author: {id, displayName}`; `author.id` совпадает с `ownerId`. Email доступен только в собственном профиле. Пользователь может изменить отображаемое имя через `PATCH /me`.

Публикация закрепляет конкретную готовую версию. Новая генерация не меняет публикацию до явного повторного `PUT /games/{gameId}/publication`. Название и описание общие для игры: их изменение сразу отражается в каталоге, не меняя опубликованную версию игры. После снятия с публикации ранее выданные ссылки могут действовать до истечения срока.

**7.2. Асинхронное взаимодействие**

Для передачи заданий между Core Service и AI Generation Service используется Apache Kafka.

Основные топики:
- `game.generation.request` — запросы на создание и изменение игр.
- `game.generation.result` — события `STARTED`, `SUCCEEDED`, `FAILED`.

Жизненный цикл задания:

1. Android отправляет запрос на создание или изменение игры.
2. Core Service в одной транзакции сохраняет задание и запись Transactional Outbox в PostgreSQL.
3. Core Service возвращает идентификатор задания и HTTP 202 Accepted.
4. Задание публикуется в Kafka.
5. AI Generation Service получает сообщение, публикует STARTED и вызывает LLM API; Core переводит задание в RUNNING после получения STARTED.
6. AI Service проверяет ответ и контент, собирает и тестирует игру в песочнице, получает оценки соответствия запросу. Только после PASS сохраняет веб-пакет, закрытые исходники, отчёт допуска и манифест в RustFS.
7. AI Service публикует сообщение о завершении в Kafka.
8. Core Service проверяет результат и в одной транзакции создаёт версию игры и переводит задание в SUCCEEDED; при ошибке фиксирует FAILED.
9. Android получает статус и загружает готовую игру.

Предусматриваются статусы `QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`. Переходы: `QUEUED → RUNNING → SUCCEEDED / FAILED`; допускаются `QUEUED → FAILED` и `QUEUED → SUCCEEDED`, если результат получен раньше STARTED. Терминальные статусы не меняются. `SUCCEEDED` означает, что файлы сохранены и версия доступна через Core.

Для отслеживания состояния задания в MVP используется периодический опрос `GET /api/v1/generations/{generationId}` (polling). Создание задания требует `Idempotency-Key`; одновременно допускается одно незавершённое задание на игру. Успешная генерация создаёт новую неизменяемую версию.

**7.3. Контракт Kafka и обработка повторов**

Контракт Kafka версионируется независимо от HTTP OpenAPI. Ключ сообщения в обоих топиках — `generationId`. Общие обязательные поля: `eventId` (UUID события, сохраняется при повторной отправке), `schemaVersion` (версия контракта сообщения), `generationId`, `gameId`, `occurredAt` (UTC RFC 3339). JWT, refresh token и секреты RustFS в сообщения не включаются.

| Сообщение | Дополнительные поля |
|---|---|
| Запрос генерации | `prompt`, `deadlineAt`, `gameSpecVersion`, `runtimeVersion`; для редактирования также `baseVersionId` и `baseManifest: {bucket, key}` |
| STARTED | `type: STARTED` |
| SUCCEEDED | `type: SUCCEEDED`, `manifest: {bucket, key}` |
| FAILED | `type: FAILED`, `error: {code, message}` с кодами GenerationError из OpenAPI |

`baseVersionId` и `baseManifest` либо присутствуют вместе, либо отсутствуют. Core проверяет принадлежность исходной версии игре до постановки задания. Передаются постоянные ключи объектов, а не временные подписанные URL. AI читает исходный пакет с собственными служебными правами RustFS; доступ к PostgreSQL Core ему не предоставляется.

Доставка допускает повторы. Core дедуплицирует события по `eventId` и защищает бизнес-результат уникальностью `generationId` у версии. Повторный STARTED не сбрасывает сроки; STARTED после терминального результата игнорируется. Допускается получение SUCCEEDED до STARTED; Core завершает задание непосредственно из QUEUED. Повторные или конфликтующие терминальные события не меняют уже зафиксированный результат.

AI подтверждает Kafka-запрос только после подтверждённой публикации терминального события. До отправки он сохраняет в RustFS служебный итог задания с `eventId` и ссылкой на манифест либо ошибкой. Итог создаётся атомарно по `generationId` без перезаписи уже сохранённого итога; конкурирующая попытка использует ранее сохранённый результат. После перезапуска повторно доставленный запрос использует сохранённый итог и повторяет отправку. Если сбой случился до сохранения итога, обработка может повториться; это не должно менять уже принятый Core пакет. Файлы разных попыток пишутся в разные префиксы, завершённые пакеты неизменяемы. Обработчик Kafka поддерживает polling/heartbeat при длительном вызове LLM; подтверждение offset не пропускает незавершённые задания той же партиции.

Core подтверждает событие результата после фиксации транзакции. Проверяются соответствие `generationId` и `gameId`, версии схемы и runtime, разрешённые ключи объектов и целостность пакета; для контракта v2 также подписанный отчёт допуска, связанный с хешем сборки (TODO реализации). При временной недоступности RustFS обработка результата повторяется до дедлайна, без преждевременного SUCCEEDED. Некорректный пакет завершает задание с INVALID_GAME_SPEC. Повреждённые сообщения изолируются в Dead Letter Topic; связанные незавершённые задания ограничены дедлайном.

**7.4. Сроки и лимиты генерации**

Начальные настройки MVP: одно активное задание на игру, не более трёх активных заданий на пользователя, общий срок задания — 10 минут с момента принятия (включая очередь и доставку результата), не более трёх попыток обращения к LLM при временных ошибках. Настройки задаются на сервере. Core возвращает фактический `deadlineAt` в Generation; повторы и события STARTED не продлевают его.

Core атомарно проверяет лимиты при принятии задания. Конфликт активного задания игры возвращает 409 (`GENERATION_IN_PROGRESS`), лимит пользователя — 429 (`GENERATION_LIMIT_EXCEEDED`) с Retry-After. Повтор уже принятого запроса с тем же Idempotency-Key и телом возвращает существующее задание до проверки лимитов, не расходуя их повторно.

Core периодически завершает просроченные QUEUED/RUNNING задания как FAILED с кодом GENERATION_TIMEOUT. При принятии результата Core также проверяет дедлайн; конкуренция результата и таймаута разрешается атомарно. Поздний результат не создаёт версию и не меняет терминальный статус. AI проверяет deadlineAt до начала работы и повторов, ограничивает сетевые таймауты оставшимся временем. Удаление игры после завершения задания не позволяет позднему сообщению восстановить игру или её версии.

### 8. Хранение данных

**PostgreSQL** используется для хранения структурированных бизнес-данных:

- Пользователи.
- Игровые проекты.
- Версии игр и ссылки на игровые файлы.
- Задания генерации.
- Публикации.
- Пользовательские оценки.
- Служебные события Transactional Outbox.

**RustFS** используется для хранения файлов:

- Дескрипторов `game.json`, HTML, JavaScript и CSS готовых проверенных игр.
- Закрытых TypeScript-исходников и отчётов допуска, недоступных через endpoint скачивания игры.
- Графических ресурсов и спрайтов.
- Звуковых ресурсов.
- Дополнительных файлов игровых проектов.

Игровые ресурсы хранятся с привязкой к конкретной версии игры. Android загружает их по временным подписанным ссылкам после проверки прав доступа через Core Service.

Внутренний манифест содержит `gameSpecVersion`, `runtimeVersion`, `gameSpec` и `assets`. В целевом формате v2 `gameSpec` — дескриптор `game.json`, а `assets` включают `index.html`, собранные JavaScript/CSS и игровые ресурсы. Закрытые `sourceArchive` и `validationReport` не входят в публичный список файлов. До внедрения v2 действующий Core проверяет только прежний формат v1; детали перехода описаны в [спецификации](docs/game-generation.md#9-пакет-исходники-и-совместимость-контрактов).

Запись файла содержит `path`, `bucket`, `key`, `mediaType`, `sizeBytes`, `sha256`. Пути уникальны и относительны, без пустых сегментов, `.` / `..`, обратных слешей и управляющих символов. Подписанные URL в манифесте не хранятся: Core формирует их при выдаче GamePackage. Поля bucket/key доступны только сервисам.

AI может читать разрешённую библиотеку и исходные пакеты, а записывать — только в префиксы генераций. Core читает результаты и выдаёт ссылки только после проверки прав. Неиспользованные результаты и незавершённые попытки очищаются после защитного периода, превышающего максимальное время задания и срок жизни подписанных ссылок; файлы сохранённых версий и исходники активных заданий не удаляются.

### 9. Надёжность и безопасность

В системе предусматриваются следующие механизмы:

- JWT-аутентификация и разграничение доступа к игровым проектам.
- HTTPS для внешнего API.
- Приватный доступ к объектному хранилищу.
- Idempotency-Key для предотвращения дублирования пользовательских заданий.
- Transactional Outbox для надёжной публикации событий из Core Service в Kafka.
- Идемпотентная обработка Kafka-сообщений.
- Повторные попытки обработки временных ошибок с ограничением числа повторов.
- Обработка неуспешных заданий и изоляция повреждённых сообщений в Dead Letter Topic.
- Ограничение времени выполнения генерации и числа параллельных заданий.
- Валидация, модерация, сборка и тестирование сгенерированного кода до загрузки игры в S3.
- Исполнение недоверенного кода только в изолированном runner и ограниченном WebView без доступа к секретам и API приложения.
- Обязательная оценка соответствия исходному запросу; отсутствие допуска блокирует выдачу.
- Централизованное журналирование ошибок и ключевых операций.

### 10. Нефункциональные требования

**Масштабируемость:** возможность независимого увеличения числа экземпляров AI Generation Service при возрастании количества запросов генерации.

**Отказоустойчивость:** сохранение задания до начала обработки, восстановление обработки после временных сбоев и защита от повторного применения результата.

**Производительность:** генерация выполняется в фоновом режиме, не блокируя обработку обычных пользовательских запросов.

**Расширяемость:** возможность добавления новых типов игровых объектов, механик и поддерживаемых жанров путём развития Phaser-заготовок, библиотеки ресурсов и контрактов веб-пакета.

**Поддерживаемость:** модульная организация исходного кода, описание API и контрактов сообщений, автоматизированные тесты.

**Безопасность:** изоляция пользовательских данных, контроль доступа к ресурсам, проверка входных данных и сгенерированных исходников, ресурсов и веб-пакетов.

### 11. Тестирование

Планируется проведение следующих видов тестирования:

- Модульное тестирование бизнес-логики и валидаторов.
- Интеграционное тестирование REST API и PostgreSQL.
- Интеграционное тестирование обмена сообщениями через Kafka.
- Проверка загрузки и сохранения объектов в RustFS.
- Проверка обработки повторных сообщений и ошибок генерации.
- Сборка и браузерные сценарии для эталонных игр Phaser.
- Проверка изоляции runner и WebView, модерации, соответствия запросу и запрета выдачи непроверенных игр.
- Сквозное тестирование сценариев создания, редактирования, запуска и публикации игр.
- Проверка работоспособности Android-приложения на целевых устройствах.

### 12. Границы первоначальной версии (MVP)

Первоначальная версия PlayLy должна обеспечивать:

1. Регистрацию и авторизацию пользователей.
2. Генерацию игр как минимум двух поддерживаемых типов.
3. Запуск сгенерированных игр внутри Android-приложения.
4. Изменение существующих игр текстовыми запросами.
5. Сохранение игровых проектов и их версий.
6. Публикацию игр в общем каталоге.
7. Просмотр, запуск и оценку опубликованных игр.

Генерация ограниченного TypeScript-кода Phaser входит в MVP. Не входят в обязательный MVP: произвольные npm-зависимости и серверный код игр, многопользовательский режим в реальном времени, сложные 3D-игры, обучение собственной LLM и генерация графики/звука. TODO: уточнить расширения после MVP.

### 13. Планируемый результат

Результатом проекта станет работоспособное Android-приложение PlayLy и связанная с ним серверная инфраструктура, обеспечивающие полный цикл создания, изменения, хранения, запуска и публикации интерактивных 2D-игр с использованием генеративного искусственного интеллекта.

В рамках проекта будут разработаны основной серверный сервис, отдельный сервис AI-генерации, Phaser-заготовки и WebView-плеер, мобильное приложение и система асинхронного взаимодействия на базе Apache Kafka.

Разработанная архитектура предусматривает возможность дальнейшего расширения библиотеки игровых механик, подключения других LLM и независимого масштабирования вычислительно затратной обработки AI-запросов.

### 14. Каркас и локальный запуск

| Каталог | Что есть сейчас |
|---|---|
| `mobile/` | Android-приложение с одним экраном на Kotlin и Jetpack Compose |
| `backend/` | Core Service на Java 25 и Spring Boot 4.1 с REST API, PostgreSQL, Kafka и RustFS |
| `ai/` | Java 25, процесс-заглушка AI Generation Service |
| `compose.yaml` | Traefik, Core, AI, PostgreSQL, Redis, Kafka в режиме KRaft, RustFS и Langfuse с локальными томами |

Core обслуживает маршруты `/api/v1` из OpenAPI и применяет миграции Flyway при старте. PostgreSQL доступен только в сети Core и БД. В текущем каркасе AI работает как заглушка. Чтобы получить готовую версию, нужен воркер, который сохранит пакет и пришлёт событие `SUCCEEDED`. Без события задание завершится по дедлайну.

#### Структура Core

Исходники в `backend/src/main/java/com/playly/core/` сгруппированы по области ответственности.

| Пакет | Что внутри |
|---|---|
| `auth` | Регистрация, профиль, refresh-сессии и лимиты auth-запросов |
| `games` | Игры и каталог, версии, публикации, оценки и проверка доступа |
| `generation` | Приём заданий, история, дедлайны, outbox и обработка Kafka-результатов |
| `storage` | RustFS, проверка пакетов и очистка объектов |
| `security` | JWT, настройки Spring Security и извлечение пользователя из токена |
| `web` | Общий формат HTTP-ошибок и курсоры пагинации |

#### Решения в Core

- **HTTP и данные.** Spring MVC контроллеры разделены по областям API. OpenAPI остаётся контрактом клиента. Core генерирует интерфейсы и модели, а HTTP-ответы описывает небольшими Java records, чтобы сохранять явные `null` в карточках и страницах и опускать поля, неприменимые к состоянию генерации. Для блокировок, условных записей и keyset-пагинации Core использует SQL через `JdbcClient`. Курсор привязан к списку и параметру поиска.
- **Авторизация.** Access JWT подписывается HS256 и действует 15 минут. Refresh-сессия действует 30 дней, при обновлении Core атомарно заменяет её токен. PostgreSQL хранит SHA-256 случайного refresh token и PBKDF2-хеш пароля. Лимит auth-операций по умолчанию составляет 30 запросов в минуту на IP. За Traefik Core использует адрес клиента, обработанный Tomcat.
- **Генерация.** Блокировка пользователя сериализует приём заданий в разных играх, блокировка игры защищает от гонок с удалением и публикацией. Запись задания и outbox фиксируются одной транзакцией. Публикатор удаляет outbox-запись после подтверждения Kafka, поэтому после сбоя возможна повторная доставка с прежним `eventId`. Core фиксирует полученное событие и переход состояния в одной транзакции. Уникальный `generationId` у версии исключает её повторное создание. Ключи идемпотентности хранятся вместе с историей игры.
- **Пакеты.** Бакет по умолчанию — `playly-games`. Воркер пишет манифест по ключу `generations/{generationId}/{attemptId}/manifest.json`, а файлы пакета — под тем же префиксом попытки. Core проверяет версии, пути, размеры, SHA-256 и то, что `game.json` содержит JSON-объект. Лимиты на манифест, GameSpec и весь пакет составляют 1, 4 и 64 МиБ соответственно. Это реализация прежнего контракта v1. Core хранит проверенный манифест и подписывает GET-ссылки на пять минут. Фоновая очистка защищает активные попытки и сохранённые версии. После удаления игры ранее выданные ссылки сохраняют доступ на свой срок.
- **Настройки окружения.** Для развёртывания задайте собственный `PLAYLY_JWT_SECRET` длиной от 32 байт и HTTPS-адрес RustFS в `S3_PUBLIC_ENDPOINT`, доступный клиенту. Служебную пару Core задают `PLAYLY_S3_ACCESS_KEY` и `PLAYLY_S3_SECRET_KEY` с правами на чтение, перечисление и очистку объектов в бакете игр. В локальном Compose используются демонстрационные учётные данные и HTTP-адрес RustFS на loopback. Для Android-эмулятора задайте доступный ему адрес RustFS (например, `http://10.0.2.2:9000`).

Для локального запуска нужен Docker с Compose.

```sh
cp .env.example .env
docker compose up -d --build
curl --fail http://localhost:8080/actuator/health
```

Traefik принимает локальные HTTP-запросы на порту `CORE_PORT` из `.env` (по умолчанию 8080) и проксирует `/api/v1/*` и `/actuator/health` в Core. Порт контейнера Core доступен внутри Docker.

Локальный стенд использует официальный образ `rustfs/rustfs:1.0.4`. Источник образа можно задать через `RUSTFS_IMAGE` в `.env`. Одноразовый сервис `storage-init` создаёт бакеты `S3_GAME_BUCKET` (по умолчанию `playly-games`) и `langfuse` через S3 API до запуска Core и Langfuse. Повторный запуск сохраняет существующие бакеты и объекты.

Core использует AWS SDK for Java v2 с S3 API RustFS. Внутренний адрес задаётся через `S3_ENDPOINT`, клиентский адрес подписанных ссылок — через `S3_PUBLIC_ENDPOINT`. Для отдельных учётных данных Core используйте `PLAYLY_S3_ACCESS_KEY` и `PLAYLY_S3_SECRET_KEY`; соответствующего пользователя и права нужно создать в RustFS. Данные хранятся в томе `rustfs-data`, образ задаётся через `RUSTFS_IMAGE`.

Проверка S3 после запуска: `docker compose run --rm --no-deps --entrypoint /bin/sh storage-init /storage/smoke.sh`. Она проверяет запись, подписанное скачивание, список объектов и удаление в обоих бакетах, затем убирает свои временные объекты. CI также повторяет инициализацию бакетов, чтобы проверять повторный запуск.

Консоль RustFS доступна на `http://localhost:9001`, API — на `http://localhost:9000`. Учётные данные для локальной разработки заданы в `.env`. Команда `docker compose down` остановит стенд и сохранит данные в томах.

Для Android откройте `mobile/` в Android Studio с JDK 17, Gradle Wrapper 9.6.1 и Android SDK 36. Из терминала в корне репозитория можно собрать приложение командой `./mobile/gradlew -p mobile :app:assembleDebug` с теми же версиями JDK и Gradle.

Core подключается к Redis по адресу `redis:6379` внутри Docker. Пароль задаётся в `.env` через `REDIS_PASSWORD`. Redis Langfuse работает отдельно.

#### Локальный Langfuse

Langfuse запускается вместе с PlayLy командой `docker compose up -d --build`. Веб-интерфейс доступен на `http://localhost:3000`. Порт меняется через `LANGFUSE_PORT` в `.env`. На первом запуске Langfuse создаёт проект **PlayLy Local** и локального пользователя с данными из `.env.example` (`admin@playly.local` / `playly-local-admin`). Эти значения предназначены для локальной разработки.

AI ждёт готовности Langfuse и отправляет проверочный спан `playly.ai.worker.start` по внутренней сети Docker. Ключи проекта задаются через `LANGFUSE_PUBLIC_KEY` и `LANGFUSE_SECRET_KEY` до первого запуска. Для уже созданного проекта используйте его действующую пару ключей. Langfuse хранит трейсы в отдельном ClickHouse, а события пишет в бакет `langfuse` существующего RustFS. Промпты и ответы воркер пока не записывает.

### 15. CI и публикация в Docker Hub

На pull request, push в `main` и push тега `v*` GitHub Actions собирает Android APK, запускает Android Lint и тест декодирования ответа каталога. Сборки серверных образов запускают тест HTTP-маршрута Core и тест чтения Kafka-события AI. После сборки CI проверяет через Traefik каталог, регистрацию, изоляцию черновиков, идемпотентность постановки генерации, применение Kafka-результата и ротацию refresh token. После успешных проверок push в `main` или push тега публикует оба серверных образа для `linux/amd64` и `linux/arm64`.

1. Создайте репозитории `playly-core` и `playly-ai` в своём аккаунте Docker Hub.
2. В GitHub откройте **Settings → Secrets and variables → Actions**. Добавьте переменную `DOCKERHUB_USERNAME` и секрет `DOCKERHUB_TOKEN` с правом записи в эти репозитории.
3. Отправьте изменения в `main` или отправьте тег релиза, например `v0.1.0`.

У каждой публикации есть тег `sha-<полный SHA коммита>`. Push в `main` также обновляет `latest`, а push тега публикует одноимённый тег образа, например `v0.1.0`.
