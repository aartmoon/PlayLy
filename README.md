# PlayLy (ПлейЛи)
## Техническая аннотация проекта

### 1. Общая информация

**Название:** PlayLy (ПлейЛи)

**Тип проекта:** мобильное приложение с использованием искусственного интеллекта для генерации интерактивных 2D-игр.

**Целевая платформа:** Android.

**Цель проекта:** разработать мобильную платформу, позволяющую пользователям создавать, изменять, запускать и публиковать 2D-игры с помощью текстовых запросов на естественном языке без необходимости владеть навыками программирования.

### 2. Описание проекта

PlayLy — мобильная платформа для создания и распространения интерактивных 2D-игр с использованием генеративного искусственного интеллекта.

Пользователь описывает желаемую игру текстовым запросом. Система обрабатывает запрос с помощью большой языковой модели (LLM), формирует структурированную спецификацию игры и передаёт её встроенному игровому движку для запуска непосредственно на устройстве.

Пользователь может изменять существующие игры дополнительными текстовыми запросами, сохранять версии, публиковать результаты в общем каталоге, запускать игры других пользователей и оценивать их.

Особенностью проекта является использование универсального игрового движка, исполняющего игры по структурированному описанию без необходимости генерации, компиляции и исполнения произвольного программного кода.

### 4. Архитектура системы

Система проектируется на основе облегчённой микросервисной архитектуры с двумя независимо развёртываемыми серверными сервисами.

**4.1. Core Service**

Основной серверный сервис, реализующий бизнес-логику приложения и предоставляющий REST API для Android-клиента.

Внутренние модули:

- **Auth & Users** — регистрация, авторизация, профили пользователей.
- **Games & Versions** — управление играми, метаданными и версиями.
- **Catalog & Ratings** — публикация, поиск и оценки игр.
- **Generation Jobs** — создание заданий генерации, управление их состояниями и обработка результатов.
- **Storage Integration** — управление объектами в MinIO.

Core Service является владельцем основной базы данных и отвечает за согласованность пользовательских и игровых данных.

**4.2. AI Generation Service**

Независимый сервис асинхронной обработки запросов на создание и изменение игр.

Функции:
- Получение заданий из Apache Kafka.
- Подготовка промптов и контекста существующей игры.
- Взаимодействие с внешним LLM API.
- Генерация и модификация GameSpec.
- Валидация структуры и допустимых игровых механик.
- Сохранение результатов генерации в MinIO.
- Публикация сообщений об успешном выполнении или ошибке через Kafka.

Сервис не обращается напрямую к базе данных Core Service. Данные задания и ключи исходных объектов MinIO передаются через Kafka; результаты возвращаются в Core через Kafka. Авторизация пользователей, управление заданиями и создание версий остаются ответственностью Core. AI не выдаёт пользовательские токены и не предоставляет клиентских HTTP-ручек.

**4.3. Android Application**

Мобильный клиент содержит пользовательский интерфейс и встроенный игровой движок.

Основные компоненты:
- Авторизация и профиль.
- Редактор текстовых запросов.
- Управление игровыми проектами.
- Каталог опубликованных игр.
- Game Loader — загрузка и кеширование игровых файлов.
- Game Runtime — интерпретация и исполнение игровых спецификаций.
- 2D Renderer — отрисовка игровых объектов и сцены.

### 6. Генерация и исполнение игр TODO махач

Основой системы является GameSpec — структурированное описание игры в формате JSON.

Спецификация содержит:
- Тип и параметры игры.
- Описание игровых сцен.
- Игровые объекты и их свойства.
- Начальные координаты и параметры движения.
- Поддерживаемые игровые механики.
- Правила взаимодействия объектов.
- Условия победы и поражения.
- Ссылки на графические и звуковые ресурсы.

При создании игры LLM формирует GameSpec в соответствии с заранее определённой схемой и набором поддерживаемых возможностей игрового движка.

При редактировании AI получает исходную спецификацию и дополнительный запрос пользователя, после чего создаёт новую версию GameSpec.

Встроенный движок (предварительный выбор — libGDX; окончательное решение отмечено TODO в стеке) загружает спецификацию, создаёт игровые объекты и исполняет их поведение с использованием заранее реализованных игровых компонентов и механик.

В первоначальной версии проекта предусматривается поддержка ограниченного набора жанров и механик. Произвольный исполняемый код, полученный от LLM, не выполняется.

До реализации необходимо согласовать JSON Schema GameSpec, два поддерживаемых жанра, перечень механик и эталонные спецификации для каждого жанра (TODO). Генерация ограничена этим перечнем; запрос неподдерживаемой механики завершается ошибкой `UNSUPPORTED_GAME_REQUEST`.

В MVP используются подготовленные графические и звуковые ресурсы; генерация изображений и звука не является обязательной. AI выбирает ресурсы из разрешённой библиотеки и включает их в пакет либо создаёт игру без внешних ресурсов. GameSpec ссылается только на относительные пути пакета, а не на произвольные сетевые URL.

Core задаёт целевые `gameSpecVersion` и `runtimeVersion` при создании задания. AI обязан сформировать пакет для этих версий. `gameSpecVersion` — точная версия схемы; `runtimeVersion` — минимальная версия runtime в формате SemVer. Android проверяет поддержку схемы и совместимость runtime: одинаковый major и установленная версия не ниже требуемой. Несовместимый пакет не запускается; приложение предлагает обновление. Изменение несовместимых возможностей требует новой major-версии runtime.

### 7. Взаимодействие компонентов

**7.1. Синхронное взаимодействие**

Android взаимодействует с Core Service по HTTPS посредством REST API.

Используется для:
- Регистрации и авторизации.
- Получения профиля и списка игр.
- Просмотра каталога.
- Отправки заданий на генерацию.
- Получения статуса генерации.
- Публикации и оценки игр.

Контракт внешнего API описан в [OpenApi.yml](OpenApi.yml). Все HTTP-ручки реализует Core Service; AI Generation Service взаимодействует с ним через Kafka.

Регистрация и вход выполняются по email и паролю в Core. Email уникален без учёта регистра и нормализуется удалением пробелов по краям; пароль не нормализуется и хранится только как стойкий хеш. Core выдаёт JWT access token и непрозрачный refresh token. Сроки действия возвращаются в секундах в `expiresIn` и `refreshExpiresIn`.

При обновлении refresh token атомарно заменяется и становится недействительным после использования. Клиент обновляет токены последовательно. Выход отзывает указанную refresh-сессию; уже выданный access token действует до истечения срока. Клиент удаляет оба токена.

Каталог, карточки опубликованных игр, метаданные опубликованных версий и ссылки на их пакеты доступны без входа. Если клиент передал недействительный access token, возвращается 401. Черновики и история версий и генераций доступны только владельцу. Отсутствующий или недоступный ресурс возвращает 404. Оценки требуют авторизации и относятся к игре, сохраняясь при смене опубликованной версии. Все операции с оценкой доступны только для опубликованной игры; после снятия с публикации возвращается 404, сохранённые оценки вновь доступны при повторной публикации. Автор не может оценить собственную игру: PUT возвращает 409 с кодом `SELF_RATING_FORBIDDEN`.

Карточка игры содержит публичные данные автора `author: {id, displayName}`; `author.id` совпадает с `ownerId`. Email доступен только в собственном профиле. Пользователь может изменить отображаемое имя через `PATCH /me`.

Публикация закрепляет конкретную готовую версию. Новая генерация не меняет публикацию до явного повторного `PUT /games/{gameId}/publication`. Название и описание общие для игры: их изменение сразу отражается в каталоге, не меняя опубликованную версию GameSpec. После снятия с публикации ранее выданные ссылки могут действовать до истечения срока.

**7.2. Асинхронное взаимодействие**

Для передачи заданий между Core Service и AI Generation Service используется Apache Kafka.

Основные топики:
- `game.generation.request` — запросы на создание и изменение игр.
- `game.generation.result` — события `STARTED`, `SUCCEEDED`, `FAILED`.

Жизненный цикл задания:

1. Android отправляет запрос на создание или изменение игры.
2. Core Service в одной транзакции сохраняет задание и запись Transactional Outbox в PostgreSQL.
3. Core Service возвращает идентификатор задания и HTTP 202 Accepted.
4. Задание публикуется в Kafka.
5. AI Generation Service получает сообщение, публикует STARTED и вызывает LLM API; Core переводит задание в RUNNING после получения STARTED.
6. AI Service валидирует результат и сохраняет GameSpec, ресурсы и манифест пакета в MinIO.
7. AI Service публикует сообщение о завершении в Kafka.
8. Core Service проверяет результат и в одной транзакции создаёт версию игры и переводит задание в SUCCEEDED; при ошибке фиксирует FAILED.
9. Android получает статус и загружает готовую игру.

Предусматриваются статусы `QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`. Переходы: `QUEUED → RUNNING → SUCCEEDED / FAILED`; допускаются `QUEUED → FAILED` и `QUEUED → SUCCEEDED`, если результат получен раньше STARTED. Терминальные статусы не меняются. `SUCCEEDED` означает, что файлы сохранены и версия доступна через Core.

Для отслеживания состояния задания в MVP используется периодический опрос `GET /api/v1/generations/{generationId}` (polling). Создание задания требует `Idempotency-Key`; одновременно допускается одно незавершённое задание на игру. Успешная генерация создаёт новую неизменяемую версию.

**7.3. Контракт Kafka и обработка повторов**

Контракт Kafka версионируется независимо от HTTP OpenAPI. Ключ сообщения в обоих топиках — `generationId`. Общие обязательные поля: `eventId` (UUID события, сохраняется при повторной отправке), `schemaVersion` (версия контракта сообщения), `generationId`, `gameId`, `occurredAt` (UTC RFC 3339). JWT, refresh token и секреты MinIO в сообщения не включаются.

| Сообщение | Дополнительные поля |
|---|---|
| Запрос генерации | `prompt`, `deadlineAt`, `gameSpecVersion`, `runtimeVersion`; для редактирования также `baseVersionId` и `baseManifest: {bucket, key}` |
| STARTED | `type: STARTED` |
| SUCCEEDED | `type: SUCCEEDED`, `manifest: {bucket, key}` |
| FAILED | `type: FAILED`, `error: {code, message}` с кодами GenerationError из OpenAPI |

`baseVersionId` и `baseManifest` либо присутствуют вместе, либо отсутствуют. Core проверяет принадлежность исходной версии игре до постановки задания. Передаются постоянные ключи объектов, а не временные подписанные URL. AI читает исходный пакет с собственными служебными правами MinIO; доступ к PostgreSQL Core ему не предоставляется.

Доставка допускает повторы. Core дедуплицирует события по `eventId` и защищает бизнес-результат уникальностью `generationId` у версии. Повторный STARTED не сбрасывает сроки; STARTED после терминального результата игнорируется. Допускается получение SUCCEEDED до STARTED; Core завершает задание непосредственно из QUEUED. Повторные или конфликтующие терминальные события не меняют уже зафиксированный результат.

AI подтверждает Kafka-запрос только после подтверждённой публикации терминального события. До отправки он сохраняет в MinIO служебный итог задания с `eventId` и ссылкой на манифест либо ошибкой. Итог создаётся атомарно по `generationId` без перезаписи уже сохранённого итога; конкурирующая попытка использует ранее сохранённый результат. После перезапуска повторно доставленный запрос использует сохранённый итог и повторяет отправку. Если сбой случился до сохранения итога, обработка может повториться; это не должно менять уже принятый Core пакет. Файлы разных попыток пишутся в разные префиксы, завершённые пакеты неизменяемы. Обработчик Kafka поддерживает polling/heartbeat при длительном вызове LLM; подтверждение offset не пропускает незавершённые задания той же партиции.

Core подтверждает событие результата после фиксации транзакции. Проверяются соответствие `generationId` и `gameId`, версии схемы и runtime, разрешённые ключи объектов и целостность пакета. При временной недоступности MinIO обработка результата повторяется до дедлайна, без преждевременного SUCCEEDED. Некорректный пакет завершает задание с INVALID_GAME_SPEC. Повреждённые сообщения изолируются в Dead Letter Topic; связанные незавершённые задания ограничены дедлайном.

**7.4. Сроки и лимиты генерации**

Начальные настройки MVP: одно активное задание на игру, не более трёх активных заданий на пользователя, общий срок задания — 10 минут с момента принятия (включая очередь и доставку результата), не более трёх попыток обращения к LLM при временных ошибках. Настройки задаются на сервере. Core возвращает фактический `deadlineAt` в Generation; повторы и события STARTED не продлевают его.

Core атомарно проверяет лимиты при принятии задания. Конфликт активного задания игры возвращает 409 (`GENERATION_IN_PROGRESS`), лимит пользователя — 429 (`GENERATION_LIMIT_EXCEEDED`) с Retry-After. Повтор уже принятого запроса с тем же Idempotency-Key и телом возвращает существующее задание до проверки лимитов, не расходуя их повторно.

Core периодически завершает просроченные QUEUED/RUNNING задания как FAILED с кодом GENERATION_TIMEOUT. При принятии результата Core также проверяет дедлайн; конкуренция результата и таймаута разрешается атомарно. Поздний результат не создаёт версию и не меняет терминальный статус. AI проверяет deadlineAt до начала работы и повторов, ограничивает сетевые таймауты оставшимся временем. Удаление игры после завершения задания не позволяет позднему сообщению восстановить игру или её версии.

### 8. Хранение данных

**PostgreSQL** используется для хранения структурированных бизнес-данных:

- Пользователи.
- Игровые проекты.
- Версии игр и ссылки на игровые файлы.
- Задания генерации.
- Публикации.
- Пользовательские оценки.
- Служебные события Transactional Outbox.

**MinIO** используется для хранения файлов:

- JSON-спецификаций GameSpec.
- Графических ресурсов и спрайтов.
- Звуковых ресурсов.
- Дополнительных файлов игровых проектов.

Игровые ресурсы хранятся с привязкой к конкретной версии игры. Android загружает их по временным подписанным ссылкам после проверки прав доступа через Core Service.

Внутренний манифест пакета содержит `gameSpecVersion`, `runtimeVersion`, `gameSpec` и `assets`. Запись файла содержит `path`, `bucket`, `key`, `mediaType`, `sizeBytes`, `sha256`; `gameSpec.path` строго равен `game.json`, его mediaType — `application/json`. Пути всех файлов уникальны, относительны, не содержат пустых сегментов, `.` / `..`, обратных слешей и управляющих символов. Все внешние ресурсы GameSpec включены в assets. Подписанные URL в манифесте не хранятся: Core формирует их при выдаче GamePackage. Поля bucket/key доступны только сервисам.

AI может читать разрешённую библиотеку и исходные пакеты, а записывать — только в префиксы генераций. Core читает результаты и выдаёт ссылки только после проверки прав. Неиспользованные результаты и незавершённые попытки очищаются после защитного периода, превышающего максимальное время задания и срок жизни подписанных ссылок; файлы сохранённых версий и исходники активных заданий не удаляются.

### 9. Надёжность и безопасность

В системе предусматриваются следующие механизмы:

- JWT-аутентификация и разграничение доступа к игровым проектам.
- HTTPS для внешнего API.
- Приватный доступ к объектному хранилищу.
- Idempotency-Key для предотвращения дублирования пользовательских заданий.
- Transactional Outbox для надёжной публикации событий из Core Service в Kafka.
- Идемпотентная обработка Kafka-сообщений.
- Повторные попытки обработки временных ошибок с ограничением числа повторов.
- Обработка неуспешных заданий и изоляция повреждённых сообщений в Dead Letter Topic.
- Ограничение времени выполнения генерации и числа параллельных заданий.
- Валидация GameSpec перед сохранением и запуском.
- Запрет исполнения произвольного кода, сгенерированного моделью.
- Централизованное журналирование ошибок и ключевых операций.

### 10. Нефункциональные требования

**Масштабируемость:** возможность независимого увеличения числа экземпляров AI Generation Service при возрастании количества запросов генерации.

**Отказоустойчивость:** сохранение задания до начала обработки, восстановление обработки после временных сбоев и защита от повторного применения результата.

**Производительность:** генерация выполняется в фоновом режиме, не блокируя обработку обычных пользовательских запросов.

**Расширяемость:** возможность добавления новых типов игровых объектов, механик и поддерживаемых жанров путём развития схемы GameSpec и игрового движка.

**Поддерживаемость:** модульная организация исходного кода, описание API и контрактов сообщений, автоматизированные тесты.

**Безопасность:** изоляция пользовательских данных, контроль доступа к ресурсам, проверка входных данных и сгенерированных игровых спецификаций.

### 11. Тестирование

Планируется проведение следующих видов тестирования:

- Модульное тестирование бизнес-логики и валидаторов.
- Интеграционное тестирование REST API и PostgreSQL.
- Интеграционное тестирование обмена сообщениями через Kafka.
- Проверка загрузки и сохранения объектов в MinIO.
- Проверка обработки повторных сообщений и ошибок генерации.
- Тестирование игрового движка на наборе эталонных GameSpec.
- Сквозное тестирование сценариев создания, редактирования, запуска и публикации игр.
- Проверка работоспособности Android-приложения на целевых устройствах.

### 12. Границы первоначальной версии (MVP)

Первоначальная версия PlayLy должна обеспечивать:

1. Регистрацию и авторизацию пользователей.
2. Генерацию игр как минимум двух поддерживаемых типов.
3. Запуск сгенерированных игр внутри Android-приложения.
4. Изменение существующих игр текстовыми запросами.
5. Сохранение игровых проектов и их версий.
6. Публикацию игр в общем каталоге.
7. Просмотр, запуск и оценку опубликованных игр.
8. Корректную обработку асинхронной генерации и ошибок.

Не входят в обязательный MVP: генерация произвольного исполняемого кода, многопользовательский режим в реальном времени, создание сложных 3D-игр, собственное обучение LLM и поддержка произвольных игровых механик за пределами возможностей движка. (?? TODO)

### 13. Планируемый результат

Результатом проекта станет работоспособное Android-приложение PlayLy и связанная с ним серверная инфраструктура, обеспечивающие полный цикл создания, изменения, хранения, запуска и публикации интерактивных 2D-игр с использованием генеративного искусственного интеллекта.

В рамках проекта будут разработаны основной серверный сервис, отдельный сервис AI-генерации, универсальный игровой движок, мобильное приложение и система асинхронного взаимодействия на базе Apache Kafka.

Разработанная архитектура предусматривает возможность дальнейшего расширения библиотеки игровых механик, подключения других LLM и независимого масштабирования вычислительно затратной обработки AI-запросов.
