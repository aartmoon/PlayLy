# Правила интерфейса Android PlayLy

## Область применения

Интерфейс приложения строится на Jetpack Compose и Material Design 3. Правила применяются к авторизации, каталогу, редактору, профилю и Android-оболочке плеера. Игровая сцена Phaser внутри WebView следует отдельному контракту из [спецификации веб-игр](../../docs/game-generation.md).

Каркас включает общую Material-тему, spacing-токены и строки в ресурсах. Светлый и тёмный режимы монохромные. В своём режиме можно отдельно сохранить цвет фона и цвет подсветки. Логотип в шапке использует контрастный цвет темы, а иконка приложения остаётся зелёной. Карточки используют декоративные обложки, поскольку каталог Core пока не отдаёт изображения.

## Material и тема

- Используйте компоненты `androidx.compose.material3` для стандартных кнопок, полей, карточек, диалогов и навигации. Сохраняйте предусмотренные компонентом состояния, семантику и размеры интерактивных областей.
- Цвета берите из `MaterialTheme.colorScheme`, текстовые стили — из `MaterialTheme.typography`, формы — из `MaterialTheme.shapes`.
- Цветовые значения, типографика и формы определяются в общей теме. Новое визуальное значение сначала оформляется как часть темы/дизайн-системы, затем используется экраном.
- Общие компоненты должны иметь понятную ответственность и использовать Material-компоненты внутри. Выделяйте их, когда это обеспечивает единый стиль или устраняет повторение.
- Поддерживайте светлую и тёмную темы. Выбор брендовых цветов и dynamic color остаётся отдельным продуктовым решением.

## Размеры и отступы

- Layout-размеры задавайте в `dp`, размеры текста — через типографику темы с поддержкой масштабирования `sp`.
- При реализации темы создайте собственный набор spacing-токенов. Базовая шкала проекта: `0, 4, 8, 12, 16, 24, 32, 48 dp`; имена токенов отражают назначение или величину.
- Отступы экранов и расстояния между элементами берите из токенов. Размеры и внутренние отступы стандартных Material-компонентов определяются их спецификациями и default-параметрами; общая шкала их не заменяет.
- `MaterialTheme` не предоставляет встроенного набора spacing: он добавляется как собственный объект/расширение темы либо как именованные dimension-ресурсы. Выберите один способ и используйте его последовательно.
- Применяйте `start/end` для направленных отступов. Учитывайте системные панели, display cutout и IME; не применяйте одни и те же insets дважды.
- Layout должен корректно работать при изменении ширины окна, увеличенном шрифте и длинных текстах. Избегайте фиксированной высоты для блоков с многострочным содержимым.

## Строки и локализация

- Статические пользовательские строки храните в `res/values/strings.xml` соответствующего Android-модуля. Это относится к заголовкам, кнопкам, подсказкам, сообщениям ошибок и accessibility-описаниям.
- В Compose используйте `stringResource`; для вставки значений — ресурсные шаблоны с позиционными аргументами; для количественных форм — `plurals` и `pluralStringResource`.
- Не собирайте предложения конкатенацией переводимых фрагментов. Форматируйте числа и даты с учётом locale.
- Пользовательские промпты, имена, названия игр и другой серверный контент остаются данными. Технические ключи, URL и значения протокола не являются строками интерфейса.
- Коды ошибок API сопоставляйте с безопасными локализованными сообщениями; внутренние исключения не показывайте пользователю.
- Тестовые фикстуры и Preview могут использовать явно обозначенные примерные данные. Пользовательские строки, поставляемые в приложении, остаются ресурсами.

## Доступность и состояния

- Интерактивная область должна быть не меньше 48 × 48 dp. Видимая иконка может быть меньше; используйте подходящие Material-компоненты и не перекрывайте соседние области нажатия.
- Иконкам-действиям задавайте локализованное описание; декоративным изображениям — `contentDescription = null`. Сохраняйте роли, выбранное состояние и понятный порядок чтения TalkBack.
- Не обозначайте важный статус только цветом. Текст и элементы управления должны сохранять читаемость в обеих темах.
- Для сценариев с данными предусмотрите loading/content/empty/error, повтор и состояние недоступного действия там, где они применимы. Ошибка не должна уничтожать введённый промпт.
- Screen-level UI получает состояние и callbacks; операции с сетью и хранилищем выполняются по [архитектуре](architecture.md). Локальное визуальное состояние может принадлежать composable.

## Проверка экрана

- Сверьте поведение с [экранами MVP](screens.md), а компоненты — с Material Design 3.
- Проверьте значимые состояния, светлую/тёмную тему, увеличенный шрифт, длинный текст и работу с клавиатурой. При изменении адаптивного layout проверьте соответствующие размеры окна.
- Запустите Android Lint и подходящие тесты. Результат сборки не заменяет визуальную проверку; в отчёте укажите, что проверено на эмуляторе/устройстве и что осталось непроверенным.
- Автоматизируйте стабильные проверки ресурсов, семантики и пользовательских сценариев по мере появления реализации. Не считайте отсутствие lint-ошибок доказательством соблюдения всех визуальных требований.
